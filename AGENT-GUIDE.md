# Инструкция для агента: собрать kaeru-mcp на изолированной Windows-машине

Читай целиком до первой команды. Здесь описан не «примерный путь», а
проверенная последовательность: этот форк уже собирали с нуля с пустым
`CARGO_HOME` и физически отключённой сетью.

## Цель

Получить рабочий `target\release\kaeru-mcp.exe` из этого репозитория, **не
обращаясь в интернет**. Все зависимости уже лежат в `vendor/` и закоммичены.

Конечное состояние: бинарник существует, запускается и слушает
`http://127.0.0.1:9876/mcp`.

---

## Жёсткие запреты

Нарушение любого из них ломает сборку необратимо — вернуть будет нечем, сети нет.

1. **Не редактируй `Cargo.toml` и `Cargo.lock`.** Ни в корне, ни в крейтах.
   Лок соответствует `vendor/` байт-в-байт; любая правка заставит cargo
   переразрешать граф и лезть в сеть.
2. **Не запускай** `cargo update`, `cargo add`, `cargo remove`, `cargo vendor`,
   `cargo install`, `rustup update`, `rustup target add`.
3. **Не трогай `.cargo/config.toml`.** Строка `offline = true` там стоит
   намеренно. Если сборка падает с `no matching package` — это диагноз, а не
   повод включить сеть.
4. **Не удаляй и не «чисти» ничего в `vendor/`.** Каждый файл сверяется по
   SHA-256. Единственное разрешённое изменение описано в §4.1, дословно.
5. **Не меняй бэкенд хранилища.** cozo + RocksDB обязателен. Заменить его на
   sled нельзя: sled-бэкенд cozo не поддерживает time travel, а на нём стоит
   вся би-темпоральность kaeru — проверено, дисковые тесты падают.
6. **Не пытайся обойти отсутствующий тулчейн.** Если нет MSVC Build Tools или
   libclang — это установка с правами администратора. Останавливайся и
   докладывай человеку (§6), не изобретай обходные пути кроме §4.1.

---

## Шаг 0. Снять факты об окружении

Выполни всё и **сохрани вывод целиком** — он понадобится в отчёте.

```bat
rustc -vV
cargo -V
where cl
where link
where clang
where cmake
where nasm
echo %LIBCLANG_PATH%
```

Как читать результат:

| Что смотрим | Норма | Если не так |
|---|---|---|
| `rustc` версия | **1.88.0 или выше** | Стоп. Более старый rustc не соберёт edition 2024. Доложить человеку — лок надо пересобирать под их версию на машине с интернетом |
| `host:` в выводе `rustc -vV` | `x86_64-pc-windows-msvc` (ожидаемый) либо `x86_64-pc-windows-gnu` | Запомни, какой именно. Всё вендорилось под обе версии, но диагностика ошибок различается |
| `cl.exe` найден | да | Нет → нет MSVC Build Tools. Стоп, §6 |
| `clang.exe` или `LIBCLANG_PATH` | хотя бы одно | Нет → см. §4.1, там штатный обход |
| `cmake`, `nasm` | **не нужны** | Отсутствие — нормально, ничего не делай |

Не устанавливай ничего сам. Ты только фиксируешь факты.

## Шаг 1. Клонировать и проверить целостность

```bat
git -c core.autocrlf=false clone https://github.com/1Croydan1/kaeru-offline.git
cd kaeru-offline
```

Флаг `core.autocrlf=false` обязателен. В репозитории есть `.gitattributes` с
`* -text`, но если системный git-конфиг навязывает `autocrlf=true`, флаг снимает
любые сомнения. Конвертация переводов строк переписывает байты вендора и ломает
**все** контрольные суммы разом.

Если git ругается `Filename too long`:

```bat
git config --global core.longpaths true
```
и клонируй заново.

Проверка, что дерево доехало целиком (PowerShell):

```powershell
(git ls-files vendor | Measure-Object -Line).Lines
```

Должно быть ровно **26418**. Меньше — сканер безопасности что-то вырезал по
дороге; сборка всё равно упадёт, лучше узнать сейчас. Доложить человеку с
указанием фактического числа.

## Шаг 2. Переменные окружения

```bat
set AWS_LC_SYS_PREBUILT_NASM=1
```

Это заменяет NASM готовыми объектными файлами, которые лежат в
`vendor\aws-lc-sys-0.41.0\builder\prebuilt-nasm\`. Без переменной сборка
потребует установленный NASM.

Если `clang` нашёлся, но `LIBCLANG_PATH` пуст — задай его на каталог с
`libclang.dll`, например:

```bat
set LIBCLANG_PATH=C:\Program Files\LLVM\bin
```

В PowerShell то же самое пишется как `$env:AWS_LC_SYS_PREBUILT_NASM = "1"`.
Переменные живут только в текущей сессии — если открываешь новое окно,
выставляй заново.

---

## Шаг 3. Сборка

```bat
cargo build --release -p kaeru-mcp
```

Ожидаемое: несколько минут (на референсной машине — 2 мин 48 с), самое долгое —
компиляция RocksDB из C++. Вывод вида `Compiling cozorocks v0.1.7` — это норма,
а не зависание.

Не добавляй `--offline`: он уже включён в `.cargo/config.toml`. Не добавляй
`--all-features` и не собирай `--workspace` — нужен только `kaeru-mcp`.

## Шаг 4. Если упало

Найди свою ошибку. Действуй строго по таблице, не импровизируй.

| Ошибка | Что это | Действие |
|---|---|---|
| `Unable to find libclang` / `couldn't find libclang.dll` | `zstd-sys` генерирует биндинги через bindgen | §4.1 — штатный обход, LLVM не нужен |
| `checksum mismatch for ...` / `failed to verify the checksum` | Файл изменился по дороге | §4.2 |
| `failed to open file vendor\...` + `No such file or directory` | Файл не доехал | §4.2 |
| `no matching package named ... found` | В `vendor/` нет крейта из лока | Стоп. Дерево неполное, чинить здесь нечем. §6 |
| `link.exe not found` / `cl.exe not found` / `could not find native static library` | Нет MSVC Build Tools или активен не тот тулчейн | Стоп, §6 |
| `nasm.exe not found` | Не выставлена переменная | Вернись к §2, задай `AWS_LC_SYS_PREBUILT_NASM=1` |
| `Filename too long` | Лимит пути Windows | `git config --global core.longpaths true`, клонировать заново |
| Сборка встаёт колом на `cozorocks` без ошибки | Нехватка памяти при компиляции C++ | Пересобрать с `cargo build --release -p kaeru-mcp -j 1` |
| Что-то ещё | — | Не гадай. §6, приложи полный вывод |

### 4.1. Обход, если libclang недоступен

Разрешён только этот, и только дословно. Он не меняет версий зависимостей — у
`zstd-sys` есть собственные заранее сгенерированные биндинги
(`src/bindings_zstd.rs`), надо лишь выключить дефолтную фичу `bindgen`.

Шаг 1. Открой `vendor\zstd-sys-2.0.16+zstd.1.5.7\Cargo.toml`, найди блок
`[features]` и в списке `default` удали строку `"bindgen",`. Остальные элементы
(`"legacy"`, `"zdict_builder"`) оставь на месте.

Шаг 2. Открой `vendor\zstd-sys-2.0.16+zstd.1.5.7\.cargo-checksum.json`.
Там длинный JSON вида `{"files":{...много...},"package":"<хеш>"}`. Скопируй
значение `package` и замени весь файл на:

```json
{"files":{},"package":"<тот самый хеш, ничего не меняя>"}
```

Пустой `files` отключает пофайловую сверку **только для этого крейта** — иначе
cargo увидит правку из шага 1 и упадёт.

Шаг 3. Повтори §3. Проверь, что в выводе больше нет `Compiling bindgen`.

Ничего другого в `vendor/` не правь.

### 4.2. Битые или пропавшие файлы

Cargo называет конкретный файл. Сначала попробуй восстановить чекаут:

```bat
git config core.autocrlf false
git checkout -- .
```

Пересобери. Если ошибка та же — файл не доехал с сервера (вероятнее всего его
вырезал сканер безопасности). Здесь это не чинится: нужен человек, который
донесёт файл отдельно. Доложи имя файла дословно, §6.

## Шаг 5. Проверить результат

```bat
dir target\release\kaeru-mcp.exe
```

Тесты (тоже офлайн, ~1–2 минуты):

```bat
cargo test -p kaeru-core -p kaeru-mcp
```

Все должны пройти. Падения дисковых тестов — сигнал, что что-то не так с
подложкой, докладывай.

Запуск демона:

```bat
target\release\kaeru-mcp.exe
```

Ожидаемое: процесс не завершается и пишет в лог строки про `listen_address`,
`listen_port` и `kaeru substrate ready`. По умолчанию слушает
`http://127.0.0.1:9876/mcp`, хранилище создаёт в
`%LOCALAPPDATA%\ai.lamantin.kaeru`.

Тюнится переменными `KAERU_MCP_*` (например `KAERU_MCP_LISTEN_PORT`) и
`KAERU_VAULT_PATH`. Облачный тир не настраивай — он для изолированной машины не
нужен и требует сети.

Останови процесс (Ctrl+C) — на этом задача выполнена.

---

## Шаг 6. Что доложить человеку

Отчёт в любом случае, успех или нет. Обязательно приложи:

1. Полный вывод команд из §0 — версия rustc, `host:`, что из тулчейна нашлось.
2. Число файлов из §1.
3. Применялся ли обход §4.1 (да/нет).
4. При падении — **полный** вывод cargo, а не пересказ. Первая ошибка важнее
   последней: cargo часто добавляет каскад «could not compile» поверх настоящей
   причины.
5. При успехе — время сборки и размер `kaeru-mcp.exe` (ожидаемый порядок —
   десятки мегабайт).

Не сообщай об успехе, пока `dir` из §5 не показал файл. Не «чини» ничего за
пределами §4.1 — на этой машине откатиться неоткуда.
